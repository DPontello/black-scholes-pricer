## 2. Como retomar em outro PC

```bash
git clone https://github.com/DPontello/black-scholes-pricer.git   # ou: git fetch origin
cd black-scholes-pricer
git switch development && git pull
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[dev,app]"                # Linux: .venv/bin/python
npm --prefix frontend ci
```

Gates (com `PYTHONPATH=src`; no Linux troque `.venv/Scripts/` por `.venv/bin/`):

```bash
.venv/Scripts/python -m pytest -q -p no:cacheprovider --cov
.venv/Scripts/python -m mypy
.venv/Scripts/python -m ruff check .
.venv/Scripts/python -m ruff format --check .
.venv/Scripts/lint-imports --no-cache
npm --prefix frontend run verificar
npm --prefix frontend run build
```

Esperado (05/11, depois da semana 5, no Linux): 5430 testes Python (cobertura 98,49%) e 273 do
frontend. Em 04/11, no Windows: 5370 testes Python (21 pulados) e 235 do frontend (§10).

Para abrir o app: `python -m options_engine app` (`--sem-ponte` sem o Tryd, `--sem-janela`,
`--porta N`). Os dados do app ficam em `%APPDATA%\PainelOpcoes` (Windows) ou
`~/.config/painel-opcoes` (Linux); a carteira e as simulações ficam na **pasta do perfil** que
você escolher (nuvem ou pendrive). Num PC novo, criar o perfil apontando para a mesma pasta
**adota** o perfil que já está lá.

## 4. Como o autor gosta de trabalhar

- **Perguntas em enquete:** toda decisão do autor vai numa enquete com opções (no Claude Code,
  `AskUserQuestion`), a recomendada primeiro e com o custo de cada uma.
- **Uma tarefa por vez:** ao fim de cada tarefa, entrada no ledger da semana e a pergunta
  "commito e sigo?". O autor responde "Commitar e seguir". Por tarefa, só as checagens rápidas
  (ruff, mypy, import-linter e as suítes tocadas); o gate completo (pytest inteiro com cobertura,
  `verificar` e `build`) fica para o fim da semana, antes do PR (pedido do autor em 02/11).
- **Comentários só para um porquê não óbvio**; nada de docstring longa nem de comentário que
  repete o código.
- **Arquivos da B3 só baixados pelo autor**; o agente usa os que já estão no disco.
- **Decisão de negócio não se assume:** quando o código obriga a escolher uma regra, ela vai para o
  ledger como `Ruling:` e, se mudar o resultado para o usuário, vira enquete.
- Ao fim de uma semana: ponta a ponta com os arquivos reais, documentação (ROADMAP, README e
  HANDOFF), push, PR para a `development`, CI verde e merge `--no-ff`.

## 9. 04/11: IR mensal das opções (semana 4, parte 2)

- **O que está feito** (branch `feat/ir-mensal`, a partir da `development` local `785d324`;
  [plano](plans/2026-11-04-semana-4-parte-2-ir-mensal.md), decisões no
  [ledger](ledger-semana-4.md)):
  - a Carteira ganhou a terceira aba, **IR mensal**: uma linha por mês, a mais recente no topo,
    com resultado comum e day trade, prejuízo a compensar, base, IR do mês e "a pagar" (valor e
    prazo, ou "abaixo de R$ 10: soma com o IR dos próximos meses");
  - ao abrir o mês: a base com as alíquotas, a soma com o IR pendente de antes, as peças
    (encerramento ou pó, comum ou day trade) e a nota de cada exercício ou atribuição;
  - o glossário ganhou o termo `ir-mensal`, e a tela Telas do Aprender cita a aba.
- **Regras** (desenho §3.3, decididas em 04/11 porque o autor delegou):
  - day trade parcial: só a quantidade casada no dia, pelos preços médios do dia;
  - IR abaixo de R$ 10 soma com o dos meses seguintes; prejuízo de depois não abate IR já devido;
  - "pagar até": último dia útil do mês seguinte, pelo calendário da B3;
  - preço médio por série no perfil, juntando as operações com a mesma série;
  - custos dentro do preço (compra soma, venda desconta); pó realiza o médio inteiro; exercício
    e atribuição não entram (o prêmio vai para a ação, que fica fora da conta).
- **Conferido:** os dois meses do exemplo, à mão e no app real numa pasta temporária (outubro:
  day trade de R$ 28,00 e prejuízo comum de R$ 52,00, IR de R$ 5,60 que fica para depois;
  novembro: base de R$ 85,00, IR de R$ 12,75 + R$ 5,60 = R$ 18,35, pagar até 30/12/2026).
- **Falta, com o autor:**
  - conferir com uma nota de corretagem ou um informe real de um mês com opções;
  - quando a mesma série estiver em duas operações do perfil, o resultado por peça não bate com o
    "Realizado" de cada operação da Carteira (o total bate). Ver se isso confunde na prática.

## 10. 04/11: alertas (semana 4, parte 3)

- **Respostas do autor (04/11):** padrões de 5 dias úteis e 2% do strike, editáveis no perfil;
  stop e alvo em reais em todas as operações (também as só de ações), comparados com o resultado

  Montador, porque o Montador não aceita dois vencimentos numa estrutura (decisão nº 6).
- **O que está feito** (branch `feat/alertas`; [plano](plans/2026-11-04-semana-4-parte-3-alertas.md),
  decisões no [ledger](ledger-semana-4.md)):
  - regras puras em `domain/alerts/`: exercício a registrar, stop, risco de exercício, vencimento
    próximo, aguardando o fechamento e alvo, nessa ordem de gravidade;
  - a operação guarda o `modelo`, o `stop` e o `alvo` (campos opcionais no JSON; a `versao`
    continua 1); o perfil guarda os limites em `"alertas"`;
  - os dispensados ficam em `alertas.json` na pasta do perfil; um dispensado volta quando o alerta
    deixa de valer e vale de novo; sem preço de zerar ou sem spot, o dispensado fica;
  - rotas `/api/alertas` (lista, dispensar, restaurar, rolagem) e a mensagem `alertas` no
    WebSocket, da mesma leitura da Carteira;
  - a aba Alertas (era "em breve"), "Alertas (N)" no menu, o botão Stop e alvo na Carteira, os
    campos no registro, a faixa de rolagem no Montador e três termos no glossário.
